## Compatibility decision

The registry's newest TypeScript release was 7.0.2, while `typescript-eslint@8.67.0`, used by
`eslint-config-next@16.3.2`, declares `typescript >=4.8.4 <6.1.0`. TypeScript 6.0.3 is therefore
the newest compatible release for this production baseline. See ADR 0007.

The registry's newest ESLint release was 10.8.1, but `eslint-plugin-react`,
`eslint-plugin-import` and `eslint-plugin-jsx-a11y`, bundled by `eslint-config-next@16.3.2`, still
declare ESLint 9 as their maximum supported major. `eslint-plugin-react-hooks@7.1.1` and
`typescript-eslint@8.67.0` already accept 10; three plugins are what holds the baseline, and naming
them is what lets the next reader check whether it still does. ESLint 9.39.5 is pinned so the lint
baseline has no out-of-range peer dependencies.

The global `cargo tauri` command was not installed. The repository intentionally uses the pinned
workspace CLI through `pnpm tauri`, so release builds do not depend on machine-global JavaScript or
Rust CLI state.

### Which database driver, and when

`HQ_CONTROL_PLANE_DATABASE_DRIVER` chooses how the control plane reaches
`HQ_CONTROL_PLANE_DATABASE_URL`. Unset means `neon`, which is what every deployment did before the
choice existed; setting it changes nothing else.

| Value                | Reaches the database by                                                 | Choose it when                                                                                                                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `neon` (the default) | `@neondatabase/serverless`, one HTTPS request per statement, no pool    | The database is Neon, wherever the control plane runs. It holds no connection between statements, so a suspended compute costs one slow request rather than a pool of dead sockets, and a serverless function pays no connection setup it cannot reuse.             |
| `postgres`           | `pg` (node-postgres) over TCP, a connection pool, real `BEGIN`/`COMMIT` | The database is a machine on the set's own network. This is the whole point of the setting: `neon()` speaks HTTPS to Neon over the public internet, so a control plane running at the shoot with the local network up and the internet down has no database at all. |

The URL does not decide this and cannot: Neon's compute speaks the wire protocol on 5432, so one
`postgresql://` string is valid for both drivers — proved on 2026-08-26 by connecting to this
project's own Neon endpoint with `pg`. What differs is the deployment, so the deployment says.

Two things to know before pointing `postgres` at Neon, which is possible and is not the intent:

- **Neon's free compute suspends after five minutes of inactivity, and every connection it held
  dies with it.** The pool absorbs that — the dead connection is discarded and the next statement
  opens a fresh one — but it is a cost the HTTP driver does not pay, because it holds nothing
  between statements. Against Neon, `neon` remains the right answer.
- **Connection-level session settings do not survive the trip.** Measured on 2026-08-26 against the
  live project: a `statement_timeout` sent as a startup parameter arrives as `0`, and a plain `SET`
  through the pooled endpoint outlives the connection being returned and is inherited by the next,
  unrelated client. The adapter therefore bounds statements in the driver and sets no server-side
  GUC; `apps/control-plane/src/db/postgresDatabase.ts` names every bound and what happens at it.

For a PostgreSQL on the set's LAN, write the connection URL's `sslmode` deliberately. `pg` currently
treats `sslmode=require` as `verify-full`, so a server with a self-signed certificate is refused;
`sslmode=disable` is the honest setting for a closed network with no certificate, and
`sslmode=no-verify` for an encrypted link with an unverifiable certificate.

`HQ_CONTROL_PLANE_TEST_DATABASE_DRIVER` is the same choice for the opt-in suites, and exists so the
eight of them can be run twice — once through each driver — rather than duplicated per driver.

### This project's own deployment target, and the ceilings that shape it

This section records where **this repository's maintainers** run the control plane, and the limits
that platform imposes on them. It is not a description of how the project has to be deployed.
Anyone else runs it from `compose.yaml` on their own machine against their own PostgreSQL, which
is a different set of capabilities and a different set of limits;
`docs/release/self-hosting.md` owns that table and this document does not repeat it.

**Deployed since 2026-08-27**, and the ceilings below are still read from documentation rather
than observed. The Vercel project is `codeilluminators/headquarters` (root directory `apps/hq`,
Node 24.x); the database is the Neon project `gremuchaya-hq-control-plane`, whose default branch
serves production and whose `vercel-preview` branch serves every preview deployment, so a preview
build never migrates or writes the shoot's group data. No blob store has been created, and
`materials.storage-grants` is reported off accordingly.

What has been observed, against a preview deployment on real PostgreSQL: `Health` with the
database dependency `SERVING`, `GetCapabilities` with `sync.realtime-admission` off and an
installation identity present, `CreateGroup`, `CreatePairingCode` and `PairDevice`. What has
**not** been observed is any of it from the packaged desktop shell, which is the half of stage 5's
acceptance that remains open, and any figure in the table below.

| Ceiling                               | Value                                              | What it decides here                                                                                                                                                                                               |
| ------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

The platform answers before the handler runs, so no control-plane error names the cause.                                     |

Provisioning was intended through the Vercel Marketplace's native Neon integration, so that one
invoice would cover both. It was **not** done that way: the Neon project was created directly, and
the two accounts bill separately. The practical consequence is that nothing writes `DATABASE_URL`
or `DATABASE_URL_UNPOOLED` into the Vercel project, so `HQ_CONTROL_PLANE_DATABASE_URL` is set
explicitly per environment and a rotated Neon password has to be copied across by hand. Either form
of the URL works, because the HTTP driver holds no connection for a pooler to manage.

### Two names for one Redis pair

Redis was provisioned the other way, through the Vercel Upstash Marketplace integration, and that
integration writes its own variable names into Production and Preview: `KV_REST_API_URL` and
`KV_REST_API_TOKEN`. The platform cannot alias one variable onto another, and copying a live token
by hand into `HQ_CONTROL_PLANE_REDIS_REST_TOKEN` is the manual credential handling this project
avoids everywhere else, so `apps/control-plane/src/config.ts` resolves the pair from either scheme:

- `HQ_CONTROL_PLANE_REDIS_REST_URL` / `HQ_CONTROL_PLANE_REDIS_REST_TOKEN` when either is set. They
  always win, because a deployment that writes them is pointing at an instance on purpose.
- `KV_REST_API_URL` / `KV_REST_API_TOKEN` otherwise.
- Neither set means the no-Redis branch, unchanged: the durable presence store, no rate limiting,
  and `Health` reporting Redis unconfigured.

A scheme is taken whole. A pair split across the two — `HQ_CONTROL_PLANE_REDIS_REST_URL` beside
`KV_REST_API_TOKEN`, or the reverse — refuses to start and names the missing half of the scheme it
selected, rather than completing the pair from the other one. The two schemes can address two
different Redis instances, and a URL paired with a token minted elsewhere either authenticates
nowhere or coordinates presence and rate limits against a database nobody chose; neither failure
would name itself at startup.

The same integration also injects `KV_URL`, `REDIS_URL` and `KV_REST_API_READ_ONLY_TOKEN`. None is
read: the first two are `rediss://` connection strings for a TCP client rather than the HTTPS REST
endpoint, and the read-only token can write neither a liveness key nor a rate-limit counter.

The names above are observed, not assumed: `vercel env ls production` on 2026-08-27 listed exactly
`REDIS_URL`, `KV_URL`, `KV_REST_API_URL`, `KV_REST_API_TOKEN` and `KV_REST_API_READ_ONLY_TOKEN`,
written into Production and Preview. The fallback matches that listing, not the integration's
documentation. Two consequences of the shared write: the next Production or Preview deploy takes
the Redis branch on its own, with no variable added by hand; and both environments address one
instance and one keyspace — coordination keys carry a group id but no environment segment, so the
collision is held off only by group ids differing between the Neon default branch and
`vercel-preview`, not by any isolation.
