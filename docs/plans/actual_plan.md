## 0. Промпт №0 и цель плана

### 0.1 Цель, выведенная из исходной задачи

Построить локальный оперативный штаб для съёмок, в котором **оператор
перестраивает приложение изнутри него самого**: включает режим редактирования,
меняет информацию и внешний вид, двигает плитки, откатывает изменения, и при
необходимости отправляет исправление в репозиторий ссылкой на issue. Всё
остальное в исходной задаче — материалы, синхронизация сессий, история,
локализация, динамические данные, нативная оболочка — обслуживает этот сценарий
или существует рядом с ним.

Отсюда три следствия, определяющие весь план:

1. **Режим редактирования — не фича, а инструмент.** На нём висит восемь
   требований. Построенный последним, он заставляет каждую настройку
   персонализации строиться дважды.
2. **Готово = оператор может этим воспользоваться на площадке.** Не «есть
   схема», не «структурные тесты зелёные», не «категория объявлена».
3. **Приложение никогда не исполняет введённые оператором HTML, CSS или
   JavaScript.** Любое редактирование — это патч против объявленного
   `SettingDefinition`, проверяемый его собственным type-guard.

### 0.3 Индекс требований R1–R31

Extracted for traceability. The wording is a label, not a restatement — the

### Materials and files

- **R1** — upload files (video/photo/documents/other) from any client, stored in
  the monorepo `shared/` folder, for viewing in the app.
- **R2** — upload new files through the application itself, via hidden settings.
- **R21** — optimized file playback.

### Personalization and edit mode

- **R3** — configure tile appearance; hide/show categories and tiles.
- **R4** — change date, time and information from inside the app.
- **R5** — a reset button per settings category, plus a global reset.
- **R6** — a very large number of personalization settings, informational and
  visual.
- **R7** — in edit mode, a floating panel with magnetic alignment to the
  application's edges, able to edit anything informational or visual.
- **R17** — instant switching between states while in edit mode.
- **R19** — every animation setting; interface settings; per-element size
  settings without breaking the interface; in edit mode, animation settings per
  tile, category, element and for the application as a whole.
- **R22** — accent-colour gradient border around the window while edit mode is
  on.

### Layout and interaction

- **R9** — pagination, filters and sorting wherever data exists.
- **R10** — elements that do not fit the current layout move to their own
  screens and tiles; no empty areas — a gap is filled by a tile that fits, or
  the remaining tiles stretch; use existing adaptive-layout solutions.
- **R11** — application-wide keybinds, with a highlighted list in settings and
  on first launch.
- **R12** — custom pop-up windows of many kinds, plus a right-click pop-up;
  disable text selection on non-interactive elements and outside edit mode;
  selection colour black on the accent background in dark theme, white in light.
- **R14** — theme and interface-style switching without breaking the interface.
- **R15** — accents via bold text.
- **R23** — `cursor: pointer` on every interactive element, tile and field, plus
  a dedicated cursor while changing a field and while resizing tiles in edit
  mode.
- **R26** — no page scroll on overflow, and no overflow in the first place;
  scrolling only inside a table's output list, never the table or the page.
- **R30** — on truncation, scroll appears on the specific panel or tile; a
  monolithic panel hides itself or adapts to the layout size.
- **R∅** — drag-and-drop reordering in interactive edit mode, with highlighted
  drop targets, a dashed line at their edges and a smooth accent-colour
  highlight. _(Folded into R7 in the plan: it is an edit-mode capability.)_

### Visual effects

- **R13** — animated application background, disableable; grid, dotted-grid and
  barber-like line patterns on focused elements and on the background, all
  configurable.
- **R16** — an optimized startup animation, configurable and disableable both in
  edit mode and in animation settings.

### Native shell

- **R18** — put as much as possible in a separate Rust layer bound to the Tauri
  shell; use TypeScript only for what Rust cannot do. Use as many native
  facilities as possible.
- **R24** — a custom window-control titlebar for Windows 11 and Windows 10,
  differing only in window rounding, using native Windows rounding rather than a
  reimplementation; on Vista/7/8/8.1 a plain square window with the custom
  titlebar.
- **R25** — titlebar settings exposed in the application's own settings:
  changeable buttons, element order, alignment of buttons and elements, room for
  useful information, and a configurable drag region for moving the window.

### Synchronization, history, localization

- **R27** — a mechanism synchronizing all other application sessions to the
  millisecond; configurable synchronization groups that sessions can join; a
  main session, or every session in the group made main, in which case all
  synchronize simultaneously and each can switch the whole group's state.
- **R28** — localization of every text element; in edit mode, configure the
  transliteration of a specific element, open a pull request with the prepared
  translation and receive a link to it.
- **R29** — history of edit-mode changes and of other settings changes, both for
  a group/all-sessions synchronization mode and for a single session; per-session
  history kept locally, plus a whole-group settings history; browsable through
  pagination with sorting and filters by date and time, by change category, and
  by individual elements.
- **R8** — from edit mode, produce a correction with a generated description and
  a link for creating a new repository issue containing the fix already made.

### Media and simulation

- **R20** — a custom player theme built on a community library, matching earlier
  references, rather than the native browser player.
- **R31** — make all charts, information and data for mainframes, servers,

### Process

- **R∅** — before starting, produce a separate `.md` file describing every step

## 1. Как читать этот документ

**Словарь статусов.** Применяется и к требованиям, и к фазам.

- **выполнено** — работает для современной web/desktop-цели, оператор может
  этим пользоваться. Отдельно объявленная legacy-цель этим не подразумевается.
- **частично** — существует реальный работающий срез, но названная часть
  отсутствует. Частично — это долг, а не прогресс.
- **отсутствует** — реализующего кода нет.
- **не проверено** — утверждение не подтверждено чтением кода или прогоном.
  Используется честно, вместо догадки.

**Что где искать.** §3 — что есть сейчас. §4 — вердикты по модулям. §7 —
порядок фич. §9 — исполняемые задачи. Полные тексты §5 (доказанная история),
§6 (реестр ошибочных утверждений) и §8 (журнал выполненного) перенесены в
`docs/plans/history.md`; здесь от них остались сводки и индекс.

**Работа идёт сессиями, и этот документ — стык между ними.** Ни одна фича здесь
не была сделана за один заход: F1 закрывалась четырьмя, F5 — девятью, F7 —
семнадцатью задачами, и между задачами лежат границы сессий, у которых нет
общей памяти. Отсюда практическое следствие, которое стоит держать в голове при
чтении:

- **Запись в §8 о «предыдущей задаче» — это то же самое усилие, а не чужой
  код.** Исполнителю, который открывает репозиторий и видит незакоммиченные
  правки, наполовину заполненный реестр или комментарий, объясняющий решение,
  которого он не помнит, — это продолжение той же работы, а не наследство от
  постороннего. Различие не косметическое: чужой код осматривают, свой —
  продолжают, и от этого зависит, будет ли решение перепроверено или переделано
  заново.
- **Ошибка здесь уже случалась.** Правки в `.claude/agents/*.md` были в одной
  из сессий описаны как «сделанные кем-то раньше» и едва не откачены; на деле
  это была незавершённая часть той же задачи. Реестр §6 существует ровно для
  таких случаев.
- **Ответственность при этом не делится.** По `AI_USAGE_POLICY.md` вклад
  отправляет и отвечает за него человек, который запустил работу, — независимо
  от того, сколько сессий и каких инструментов заняло его получение. Поэтому
  сообщения коммитов не содержат упоминаний инструментов: у коммита один автор.
  Непрерывность фиксируется здесь, где она полезна для чтения, а не в истории
  git, где она размыла бы ответственность.

## 2. Обязательные правила

Каждое из них появилось после конкретной ошибки в этом проекте. Они
распространяются на все задачи в §9 и на любую будущую работу.

### 2.1 Читай определение модуля, прежде чем судить о его поведении

Вердикт о том, как ведёт себя код, **не пишется** по выводу grep или по местам
вызова. Открой определение.

Трижды в этом проекте это правило было нарушено, и трижды вердикт оказался
неверным. Последний раз: было заявлено, что `Object.values(...)` внутри
Zustand-селектора вызывает лишние перерисовки — без чтения
`useOperationsStore`, который уже оборачивает каждый селектор в `useShallow`.
Все три случая записаны в §6.

Если проверить чтением невозможно — пиши «не проверено», а не догадку.

### 2.2 Утверждение о живой базе требует процитированного прогона

План или контрольная точка **не могут** описывать интеграционный сценарий как
пройденный, если рядом не записаны команда и её результат. «Написано, не
запускалось» — допустимый статус. Умолчание, создающее впечатление обратного, —
нет.

Это правило появилось после того, как семь сценариев PostgreSQL были записаны
как пройденные, ни разу не запустившись. При первом же запуске упали все девять,
и вскрылся настоящий дефект (§6, C6).

### 2.3 Структурные тесты — детекторы изменений, а не доказательство

Проверка формы сгенерированного SQL подтверждает построение запроса, но не
блокировки, не сериализацию и не то, что join действительно отсекает строку.
Любой шлюз, касающийся конкурентности, блокировок или persistence, требует
настоящего движка.

### 2.4 Результаты мутационного тестирования сообщаются полностью, включая выживших

Выживший мутант — это находка о тестах, а не то, что опускают. Формат: какой
мутант убил какие тесты, какие выжили и почему.

### 2.5 Не плодить дублирующие модули

Никаких шимов, реэкспортных барелей и вторых точек входа «на время перехода».
Если модуль переезжает — переезжают и все его импорты, в том же коммите. Если
правка требует нового модуля рядом с существующим, делающим то же самое, —
правка выбрана неверно.

### 2.6 Одна фича в работе

Новая не начинается, пока предыдущая в статусе «частично». Иначе девятнадцать
частичных станут двадцатью пятью.

### 2.7 Границы, которые проверяет CI, а не соглашение

- **Граница UI:** ни один файл вне `packages/ui` не импортирует
  `@base-ui/react` напрямую и не использует голые
  `<button>/<input>/<select>/<textarea>`. Проверяет
  `scripts/check-ui-boundary.mjs`. Компоненты shadcn/ui живут в
  `packages/ui/src/shadcn` именно поэтому. **Ослаблять сам скрипт, чтобы впустить
  библиотеку, — это дефект, а не решение: переезжает библиотека.**
- **Свежесть протокола:** любая правка `.proto` требует
  `pnpm --filter @gremuchaya/protocol generate` и закоммиченного результата.
  Проверяет `scripts/check-protocol-generation.mjs`.
- **Транспорт:** ConnectRPC поверх бинарного gRPC-Web. Ни REST, ни нативного
  gRPC, ни произвольного JSON (ADR 0003, ADR 0008).
- **Миграции append-only.** Изменение уже выпущенной миграции — тяжёлый дефект.
- **Учётные данные никогда не хранятся в сыром виде** — только
  purpose-separated HMAC с `hash_version`.
- **Offline-first:** desktop — это `output: 'export'` без Node-сервера в рантайме
  (ADR 0005). Никаких сетевых зависимостей на этапе сборки, включая шрифты.
- **Нет скролла страницы** (R26): скроллится панель или тело таблицы, но не
  документ.
- **Коммиты:** Conventional Commits; никаких упоминаний ИИ-ассистента —
  хук `commit-msg` их отклоняет.

### 2.8 Строгий TypeScript

`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals`,
`noUnusedParameters`, `verbatimModuleSyntax` — везде. Необязательные поля
передаются условным spread, а не явным `undefined`.

### 3.1 Что уже реализовано и работает

Перечисленное ниже сделано на уровне, который не требует доработки, и его легко
недооценить, потому что оно не видно на экране.

**Аутентификация парных устройств** (`apps/control-plane/src/sync`). Самая
сложная по корректности часть репозитория. Доказана мутационным тестированием
против живой PostgreSQL: 18 сценариев, включая гонку двух одинаковых повторов.
Учётные данные никогда не хранятся в сыром виде. Подробности — §5.

**Весь контракт `SyncService` и четыре сервиса поверх него** (F6, 2026-08-24).
Восемнадцать RPC — семнадцать объявленных плюс `GetDocumentSnapshot`, без

`MaterialService` (16), `TelemetryService` (7 из 10) и `IntegrationService` (7).

27 таблиц из 30. Доказано против живой PostgreSQL и по проводу gRPC-Web: 314
тестов в пакете.

**Клиенты к этому контракту построены (F9, F10; перемерено 2026-08-26).** В
`apps/hq` четыре ConnectRPC-клиента и один WebSocket:

**Устойчивый журнал событий группы** (`sync_events` + `group_event_sequences`).
Номер события выдаёт база одним upsert-ом, чья блокировка строки и

несёт `id`, `category`, `defaultValue`, `scope`, `description`, `editor` и
type-guard `validate`. Драфты иммутабельны, с `baseRevision`, `changedIds` и
встроенной `SettingsHistoryEvent[]`. Есть чекпоинты, import/export, publish,
`resetDraftCategory` и `resetDraftAll`.

**Локальная история настроек** (`operationsStore` + `SettingsHistoryLedger`).
Слой `personalization` уже содержит `published`, `draft`, `history`, `undoStack`,
`redoStack` и действия `applySettingsPatch`, `resetSettingsCategory`,
`resetAllSettings`, `discardSettingsDraft`, `publishSettingsDraft`,
`undoSettingsDraft`, `redoSettingsDraft`, `restoreSettingsHistoryEntry`,
`exportSettingsDraft`, `importSettingsDraft`. Леджер даёт `querySettingsHistory`
с пагинацией, фильтрами и порядком сортировки.

**Следствие, которое легко упустить:** undo/redo, сброс по категориям и история
для настроек **уже есть**. Режиму редактирования их строить не нужно — см. C10.

### 3.4 Control plane

**Перемерено 2026-08-24 после F6.** `SyncService` реализован целиком:
восемнадцать RPC — семнадцать объявленных плюс `GetDocumentSnapshot`, без

Каждая capability выводится из того, что корень композиции собрал, а не из
константы.

**Перемерено 2026-08-26, и три вещи оказались точнее, чем записано.** Первое:
`GetSettingsSchema` мёртв в любой существующей конфигурации — `schema` не
внедряется ни в одной точке сборки, поэтому метод всегда отвечает
`unimplemented`, и ни один тест его не трогает; схема живёт на клиенте.
Второе: **Redis не настроен ни в одном окружении** — `HQ_CONTROL_PLANE_REDIS_REST_*`
отсутствуют в `.env`, поэтому всегда берётся ветка `DurablePresenceStore`,
`Health` сообщает по Redis `NOT_SERVING`, а ограничитель частоты публикаций не
работает ни разу. «Подключён» здесь значит «есть код и точка вызова», а не «в
работе». Третье: `IntegrationService` отвечает `unimplemented` на три RPC —
`CreateIssue`, `CreateTranslationPullRequest`, `GetPullRequestStatus`, —
потому что корень композиции не несёт GitHub-шлюза; ни один путь кода ни разу
не обращался к github.com, все тесты подставляют шлюз.

**Перемерено 2026-08-27, второй пункт сдвинулся.** Upstash провизионирован
через Vercel Marketplace (условия принял владелец учётной записи), интеграция
записала `KV_REST_API_URL`/`KV_REST_API_TOKEN` в Production и Preview — под
своими именами, — и `config.ts` теперь берёт пару под любой из двух схем имён,
явные `HQ_CONTROL_PLANE_REDIS_REST_*` приоритетнее (§8, запись «Redis перестал
быть мёртвой поверхностью»). Живым запросом ветка с Redis пока не проверена.

Прежняя запись — «6 обработчиков RPC из 17; четыре сервиса не существуют;
история в памяти; Redis не подключён» — верна для состояния до 2026-08-24 и
оставлена здесь только как то, от чего F6 отталкивалась.

конкретный момент, а не требование к окружению и не свойство набора тестов;
записано, потому что «прогнал ещё раз, стало зелено» без объяснения — тот
самый способ, которым настоящий дефект однажды спишут на флак.

`apps/hq` до этой сессии не имел возможности тестировать компоненты вовсе;
`vitest.config.ts` теперь поддерживает `.tsx`, JSX-рантайм и алиас `@/*`.

**Оговорка правила 2.2, обязательная к этому счёту.** Требования, закрытые
клиентом синхронизации (R6 групповой, R27, R29 групповая) и загрузкой
материалов (R1, R2), **ни разу не работали против живого control plane или
живого бакета**: доказательство — подставные сокеты, RPC-клиенты и `fetch`,

доказано настолько, насколько доказуемо без развёрнутой инфраструктуры».

**Оговорка к трём из них, обязательная по правилу 2.2.** R6 (групповой
охват), R27 и R29 (групповая половина) закрыты клиентом, который **ни разу не
работал против живого control plane**: доказательство — подставные сокет и
RPC-клиенты, 59 тестов и 20 убитых мутантов, но не провод. «Выполнено» здесь
значит «построено и доказано настолько, насколько доказуемо без развёрнутого
сервера», и первое же включение на площадке — это проверка, а не формальность.

бакет.

композиции появилась (F6, задача 3), и этого оказалось недостаточно:

поэтому всегда берётся ветка `DurablePresenceStore`, `Health` отвечает по
Redis `NOT_SERVING`, а ограничитель частоты публикаций не срабатывает ни разу.
Конфигурация разбирается и валидируется — и не потребляется; это ровно тот
дефект, который C5 описывала до подключения, на один слой выше.

**`GetSettingsSchema` у `SettingsService`.** Реализация есть, `schema` не
внедряется ни в одной точке сборки, метод всегда отвечает `unimplemented`, ни
один тест его не трогает. Либо внедрить схему, либо убрать RPC из контракта:
объявленный метод, который не может ответить ни в одном развёртывании, — это
обещание без поведения.

**`GitHubIntegrationGateway`.** Интерфейс есть, реализации нет ни одной, кроме
тестовых двойников; три RPC `IntegrationService` отвечают `unimplemented`. R8 и
половина R28 работают на клиенте через prefilled-ссылки без токена — то есть
серверный путь не нужен для их закрытия, но он объявлен и мёртв.

**`FileSourcePort.watch` у `BridgeFileSource`.** Порт несёт член, `FileBridgeService`
несёт server-streaming watch на проводе, а адаптер моста не упоминает слово
`watch` ни разу: реализация одна из четырёх, нативная.

**`resetGroupElement` у `GroupSettingsPort`.** Объявлен на порту, реализован на
клиенте, вызывается только двумя тестовыми двойниками.

## 7. Порядок доставки

### 7.1 Почему по фичам, а не волнами

Прежний маршрут был упорядочен по техническим слоям: протокол → лайаут →
материалы → медиа → редактор. Он дал **девятнадцать требований в статусе
«частично»** — это отпечаток волнового подхода: волна закрывается по слою, а не
по способности, которой может воспользоваться оператор.

«Частично» здесь стоит дорого: такое нельзя показать, нельзя отдать на площадку
и, главное, нельзя **проверить**. Дефект квитанций (C6) выжил именно потому, что
горизонтальный срез — схема плюс адаптер плюс структурные тесты — выглядел
законченным, ни разу не будучи выполненным насквозь. Тот же почерк виден в C2,
C4 и C5.

Вторая причина специфична для этого проекта: есть съёмочный день
(`pnpm check:release`, `docs/release/runbook.md`). При дате вертикальные срезы
дают пригодный к работе набор в любой момент времени; волны не дают ничего до
завершения последней.

### 7.2 Правило инструмента — единственное исключение

> Если два и более требования вынуждены были бы построить свою версию чего-то —
> это инструмент, и он строится один раз заранее. Если это нужно ровно одному
> требованию — оно строит это внутри своего вертикального среза.

По этому признаку инструментов ровно четыре:

| Инструмент                                      | Требования, висящие на нём           |
| ----------------------------------------------- | ------------------------------------ |
| Оболочка режима редактирования (ядро R7)        | R4, R8, R17, R19, R22, R23, R25, R28 |
| Путь сохранения настроек (`SettingsService`)    | R3, R5, R6, R19, R29                 |
| Резолвер лайаута, применённый ко всем маршрутам | R3, R10, R26, R30                    |
| Устойчивый журнал событий                       | R8, R27, R29                         |

(«отредактировать всё что угодно… по части информационной составляющей») — это
один и тот же пункт запроса, а не два разных. F1 закрыла только половину
обещания R7: редактирование **настроек** через `applySettingsPatch`.

патча.

подключается к нему через интернет». R27 закрыт клиентом (F10), но клиент **ни
разу не работал против сервера в интернете**: он ходит на `127.0.0.1`.

Требования, уточнённые заказчиком 2026-08-26:

- на Vercel живут **и** бэкенд, **и** веб-интерфейс — штаб открывается в браузере
  с любой машины, Tauri остаётся богатым клиентом;
- база провизионируется **через Vercel** (Neon Native Integration), а не отдельной
  регистрацией — единый счёт;
- офлайн остаётся строгим: съёмочный день без сети выполняет сцены и экраны;
- **одна группа живёт в двух сетях сразу** — в сессии одновременно клиенты
  локальной сети и внешние, у внешних пинг выше;
- без сети работает локальная копия, а её пол — зашитые в сборку константы.

**Почему после F13.** Фича не строит ни одной новой способности оператора: она
доставляет уже построенные туда, где ими можно пользоваться не на одной машине.
Ставить её раньше значило бы выкладывать то, что ещё меняется.

**Три решения, принятые чтением, а не по умолчанию.**

1. **Роутер монтируется внутрь Next.js, а не деплоится отдельно.** Один origin для
   интерфейса и RPC — CORS исчезает как класс для веб-сборки.
   `registerControlPlaneRoutes` уже отделён от `connectNodeAdapter`, а
   `createFetchHandler` и пара `universalServerRequestFromFetch`/`ResponseToFetch`
   существуют в `@connectrpc/connect@2.1.2/protocol` — это второй адаптер поверх
   того же роутера, а не второй роутер (правило 2.5).
2. **На Vercel — опрос, а не сокет.** Не из-за цены: сокет принимает один инстанс,
   а публикация приходит на другой, где карта слушателей пуста, — клиент получил бы
   `ServerReady`, напечатал `LIVE` и не следовал ни за чем. Строка, говорящая LIVE
   при глухом экране, хуже честного POLL. Закрепить инстанс нельзя ни на одном
   тарифе.
3. **Мгновенность в локальной сети даёт плоскость на площадке, а не обнаружение
   соседей.** Однорангового пути в репозитории нет; `controlPlaneUrl` был написан
   ровно под «control plane — машина в LAN» (`projectSchemas.ts:74-83`).

**Опоры, которые уже стоят** (проверено чтением 2026-08-26):

- порядок событий глобален: номер выдаёт `INSERT … ON CONFLICT DO UPDATE …
RETURNING` под блокировкой строки, поэтому **порядок номеров равен порядку
  фиксации** и два процесса на одной базе не столкнутся;
- токен, выданный одной плоскостью, принимает другая: проверка — запрос по хешу,
  в таблицах сессий нет ни издателя, ни привязки к процессу. **Версия хеша обязана
  совпадать** — запрос фильтрует по версии проверяющего;
- повтор мутации между плоскостями безопасен: `mutation_receipts` в общей базе;
- курсор группы уже общий для лент (§8, 2026-08-26, коммит `7f036fe`).

**Тарифы, посчитанные под пять устройств и рабочий день 176 ч/мес.** Neon Free:
100 CU-ч — 8 ч/день даёт 60, 13 ч даёт 98, круглосуточно 180 и ломается. Vercel
Hobby: 1 млн вызовов — опрос раз в 2 с даёт 1,58 млн и ломается, от 5 с проходит.
**Самый узкий лимит не тот, о котором думают:** функция закреплена на 2 ГБ и не
настраивается, а лимит памяти 360 ГБ·ч — это 180 часов работы инстанса в месяц,
6 часов в день; тёплый инстанс весь рабочий день даёт 352 из 360. Реальный счёт —
**$0** на Hobby при опросе от 5 с и дне до 13 ч, либо **$20/мес** на Pro, где
расход $7,50 покрыт кредитом $20.

**Оговорка, которую нельзя обойти:** Hobby запрещает коммерческое использование —
«выгода кого угодно, причастного к любой части производства, включая оплачиваемого
исполнителя». Решение о хосте принимается **до живого деплоя**; план построен так,
что смена стоит счёта и переменной окружения, а не переписывания.

### 7.4 Почему такой порядок

- **F1 раньше всего** — правило инструмента: восемь требований.
- **F2–F5 до F6** — им не нужен сервер, поэтому они прямо конвертируются в
  работающую способность. Ставить control-plane в начало значило бы повторить
  прежнюю ошибку: потратить ранний бюджет там, где ничего не видно.
- **F6 до F7–F8** — групповая область и устойчивая история серверные, и условие
  выхода L1 не выполнено, пока их нет.
- **F9–F12 после** — каждая крупная и самодостаточная, ни одна не блокирует
  другую.
- **F13 последней** — закалка релиза не может предшествовать тому, что
  выпускают.

## 9. Ближайшая работа

### Сессия 2026-08-30 (продолжение): адрес плоскости, мастер сопряжения, bitmap-фоны

Три задачи, поставленные оператором со скриншотом диалога группы, на котором
основным адресом стоит `C:/Program Files/Git/api`, а внизу —
`ГРУППА НЕ СОЗДАНА: NetworkError when attempting to fetch resource.`

**1. Дефект адреса. Корень найден и он двухслойный.**

Первый слой — сборка. `docs/release/runbook.md:149` предписывает для веб-профиля
`NEXT_PUBLIC_HQ_CONTROL_PLANE_URL=/api`. Git Bash на Windows (MSYS2) переписывает
аргумент, начинающийся со слэша, в путь Windows, поэтому `/api` превращается в
`C:/Program Files/Git/api` **на сборке** и запекается в статический экспорт.
Оператор собирал десктоп именно так — `pnpm i` и `pnpm run tauri:build` из Git
Bash.

Второй слой — и он важнее, потому что чинится в коде. Адрес плоскости приходит
из трёх источников, и **проверяется только два из них**:

- ручной адрес — `safeParseControlPlaneUrl`, схема `projectConfigSchema.shape.controlPlaneUrl`:
  от одного до четырёх уникальных http(s)-адресов без учётных данных;
- `project.override.json` — та же схема;
- `NEXT_PUBLIC_HQ_CONTROL_PLANE_URL` — `parseControlPlaneAddressList`
  (`application/sync/controlPlaneLinks.ts:32`), который **делит строку по запятой
  и обрезает пробелы, и больше не делает ничего**.

Поэтому значение, которое поле ручного адреса отвергло бы по имени, проходит
через переменную сборки целиком, становится основным звеном в
`createLinkStates` и доходит до `fetch()`. Оператор вместо «адрес не похож на
адрес» читает `NetworkError` — сообщение браузера о том, что запрос не ушёл.

Требование: свести три источника к одной проверке, назвать отказ причиной, а не
сетевой ошибкой, и отдельно распознать именно случай MSYS — он воспроизводим и
будет повторяться у каждого, кто соберёт проект из Git Bash.

**2. Сопряжение в два действия.** Сейчас диалог группы — одна длинная форма: код
пары, имя устройства, кнопка входа, раскрываемое создание группы, имя группы,
секрет развёртывания, кнопка создания, и всё это на одном экране вместе с
адресом плоскости и её состоянием. Требование оператора: несколько сменяющих
друг друга экранов действий, на каждом — кнопка «Назад» со стрелкой влево, и
весь путь в пару действий.

**3. Bitmap-шейдерные фоны.** Везде в интерфейсе — анимированный растровый фон
на готовом решении, с настройками в разделе анимаций, вплоть до отключения.
Работа с анимацией на атомарном уровне UI: фон объявляется один раз и
подключается к поверхностям, а не рисуется каждым экраном заново. Интерфейс при
этом облегчается, а не утяжеляется, и получает glow-подачу.

Ограничения, которые решают выбор: десктоп — статический экспорт без сервера
(ADR 0005) и WebView2, поэтому библиотека обязана работать офлайн и лежать в
`out/`; CSP запрещает внешние источники; фон не имеет права соревноваться за
кадры с проигрывателем и картой, значит нужен предел частоты и честное
выключение по `prefers-reduced-motion` и по настройке.

### Сессия 2026-08-30: иконки и сплошная локализация — замер и план

Мандат оператора: заменить символьные глифы кнопок верхней панели на SVG-иконки
и дать переключать библиотеку иконок в персонализации; дать каждой строке,
которую видит оператор, перевод на каждый доступный язык; позволить создавать
переводы в самом приложении; защитить от ошибок и падать на английский; по
умолчанию показывать **всё** по-русски.

Замер сделан разбором AST (`typescript` 6.0.3) для исходников и **вычислением
самого модуля** для `settings-schema`, а не поиском по тексту, и исключает сами
каталоги, 52 сцены и мировой сид:

- Каталог `apps/hq/src/application/localization/messages.ts` — **310
  идентификаторов**: 304 русских, 304 английских и пространство `tokens` из
  шести строк, одинаковых во всех локалях.
- Вне каталога оператор читает ещё **1268 строк в 72 файлах**: 988 русских и
  280 английских. Это разметка экранов, подписи кнопок, `aria-label` и
  заголовки панелей, ни одна из которых не спрашивает локаль.
- `packages/settings-schema` объявляет **168 определений** в 33 категориях
  (`device` 152, `group` 16) и **39 перечислений со 169 вариантами**. Ни у
  одного нет подписи: `settingLabel` (`SchemaSetting.tsx:291`) собирает её из
  идентификатора — `tiles.presentation` становится `TILES / PRESENTATION`, — а
  варианты выводятся как `option.toUpperCase()`.
- Содержимое мира — **447 строк в сценах** и **113 в сиде** — отдельный вопрос:
  это художественный текст, а не хром, и решение по нему принимается до того,
  как его тронут.

Отсюда главный вывод, который стоит записать прямо: **русская локаль по
умолчанию уже выбрана** (`localization.locale`, значение `ru`), но оператор в
ней читает не меньше **617 английских строк** — 280 литералов, 168
сгенерированных подписей настроек и 169 вариантов перечислений. Обещание «по
умолчанию всё по-русски» нарушает не отсутствие переключателя, а то, что
подавляющая часть текста никогда не проходит через каталог.

Второй дефект того же корня: `translateWith` падает с целевой локали на
`sourceLocale` (`ru`), поэтому дыра в английской таблице показывает
англоязычному оператору русскую строку. Мандат требует обратного порядка.

**Решение по содержимому мира — два механизма, разделённые по населению.**
Хром получает `MessageId` и каталог; полнота проверяется компилятором.
Содержимое получает `LocalizedText` — объединение строки и записи «локаль →
строка» — в `packages/domain`, со схемой в `packages/config`. `MessageId` в
сцене означал бы, что `packages/domain` ссылается на каталог из `apps/hq`, то
есть прямую инверсию направления зависимостей; перенос каталога вниз хуже —
447 одноразовых строк оказались бы в одном пространстве имён с 310
переиспользуемыми, а определение сцены перестало бы читаться против
сценария. Голая строка означает «исходная локаль, ещё не переведено», поэтому
**52 файла сцен и сид не правятся вовсе**. Английскую сторону мира пишет
человек: 560 строк выдуманного английского, сочинённых машиной, никто не
сверит со сценарием, а неверная надпись на досье попадает в кадр. Пропуск не
прячется, а считается — отдельная чистая функция сообщает, сколько строк мира
ещё ждут перевода. Разделение, которое нельзя смешивать в отчётах: **тотальность
механизма — обещание, которое выполняется сразу; покрытие содержимого — число,
которое измеряется и показывается**.

**Гейт.** `scripts/check-localization.mjs` разбирает AST `apps/hq/src` и
`packages/ui/src` и считает строки, которые читает человек. Это храповик против
`scripts/localization-baseline.json`: превышение записи файла роняет гейт, и
падение ниже записи — тоже, потому что база, которую никто не опускает,
перестаёт описывать дерево и молча поглощает первый вид отказа. Площадка
`// i18n-exempt: <причина>` снимает одну строку и требует причину. Проверка
включена и в `pnpm check`, и отдельным шагом в `.github/workflows/ci.yml` —
рабочий процесс вызывает скрипты границ поодиночке, а не через `pnpm check`,
поэтому без своего шага проверка не выполнялась бы нигде, кроме машины
разработчика.

**Два дефекта границ, найденных попутно и не относящихся к переводу.**

- `apps/file-bridge/src/server.ts:574-578` отдаёт `error.message` от `ENOENT`
  прямо в `ConnectError`. Сообщение Node содержит **физический путь** —
  проверено запуском: `ENOENT: no such file or directory, open '<путь>'`. ADR
  0002 существует ровно затем, чтобы физические пути не доходили до
  интерфейса; замыкающая ветка той же функции пересылает `error.message` для
  любой неопознанной ошибки и течёт так же.
- `packages/domain/src/operations.ts:127` объявляет
  `classification: 'БЕТА' | 'АЛЬФА' | 'А1'` — отображаемый текст, записанный
  как доменное значение, и вдобавок объединение смешивает две оси: `АЛЬФА` и
  `БЕТА` — уровни, `А1` — код. Рядом `components/operations/TopBarReadouts.ts:62-64`
  выдаёт допуск устройства парами «уровень + код» (`АЛЬФА/А1`, `БЕТА/В2`,
  `ГАММА/С3`), то есть согласованно. Это разные понятия — классификация
  документа и допуск устройства, — и путать их не следует; дефект в том, что
  первое типизировано русской строкой и по одной оси не замыкается. Лечится
  перекодировкой объединения (`'alpha' | 'beta' | 'a1'`) с переносом
  отображения в `apps/hq`, а не переводом.

### Сессия 2026-08-29 — 2026-08-30: реестр §9 пройден волнами — сводка и остаток

Полная запись — в `docs/plans/history.md`, §8, «Реестр §9 пройден волнами».
Реестр ниже был разобран на **70 пунктов** и роздан волнами A, B, B2, C1, F1
и F2; каждая волна проходила гейт репозитория и уходила своими коммитами на
ветку `claude/ui-bugs-tailwind-migration-hctg85` (PR #20). Счёт по пунктам:
**закрыто 47, частично закрыто 13, открытыми осталось 10** — из последних
**шесть** не закрываются в этом окружении вовсе, им нужно железо или секреты
площадки, и каждый такой пункт помечен ниже отдельно.

Главное этой сессии — не число закрытых пунктов, а то, что **впервые за
историю репозитория группа прогнана против настоящего control plane**, и
первый же прогон нашёл три дефекта, которых не мог показать ни один
существующий тест.

1. **Пустой `public_key` — коммит `0ad33b0`.** `ControlPlaneClient.createGroup`
   и `.pair` отправляли `publicKey: ''`, а `normalizeDeviceInput` живого
   сервера пустое значение отвергает: **ни одно настоящее сопряжение не
   проходило ни разу и ни в одном окружении**. Появился порт `DeviceIdentity`
   и `BrowserDeviceIdentity` на ECDSA P-256; ключ живёт под одиннадцатым
   ключом `localStorage` `gremuchaya-hq:device-identity:v1`, публичная
   половина едет как `ecdsa-p256:<base64url SPKI>`. Записано коррекцией
   **C62**.
